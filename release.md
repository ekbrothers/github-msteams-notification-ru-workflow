# Python Package Release Strategy

This document describes how Python packages in this repository are versioned, released, and published to Nexus, and how that process coexists with releases of the repository's reusable GitHub Actions workflows.

## Summary

- Each Python package under `python/<package>/` is versioned and released independently.
- Versions, changelogs, and tags are produced automatically by [release-please](https://github.com/googleapis/release-please) from Conventional Commit PR titles.
- A PR title check enforces the Conventional Commit format on every pull request.
- Packages are published to Nexus only when release-please cuts a release for that package, so unchanged packages are never republished.
- The publish workflow fails if the tag and `pyproject.toml` version disagree, or if the version already exists on Nexus.
- Reusable workflows keep their existing repo-wide `vX.Y.Z` tags and rolling `vX` pointer. Packages do not use a rolling pointer.

## Requirements and how they are met

| # | Requirement | How it is met |
|---|---|---|
| 1 | Publish a package only when its files change | release-please only proposes a release for a package when merged commits touched that package's path |
| 2 | Per-package tag scheme | Tags follow `<package>-vX.Y.Z`; repo-wide `vX.Y.Z` and `vX` stay reserved for reusable workflows |
| 3 | Fail when the tag does not match `pyproject.toml` | Guard step in the build workflow compares the two before building |
| 4 | Block re-publishing an existing version | Guard step queries Nexus before upload and fails on a match |
| 5 | Release notes source | Per-package `CHANGELOG.md`, generated by release-please, also used as the GitHub Release body |
| 6 | Rolling major pointer for packages | Not used. Consumers pin with version specifiers (for example `~=1.2`) and resolve from Nexus, not git |
| 7 | Documentation | This document, plus a "Releasing" section in each package README and a link from `docs/CONTRIBUTING.md` |

## How it works

### Conventional Commit PR titles

The repository uses squash merges only, with the default squash commit message set to the pull request title. That means the PR title is the single commit message release-please reads. Commits on a feature branch can be written however the developer likes.

Only three things in a PR title affect releases:

| PR title starts with | Effect on the package it touches |
|---|---|
| `fix:` | Patch release (1.2.0 to 1.2.1) |
| `feat:` | Minor release (1.2.0 to 1.3.0) |
| `!` before the colon, for example `feat!:` | Major release (1.2.0 to 2.0.0) |

Other types (`docs`, `chore`, `refactor`, `test`, `build`, `ci`, `perf`, `revert`) are allowed and pass the title check, but they do not trigger a release and do not appear in the changelog.

A scope is optional. release-please assigns a commit to a package based on which files it changed, not on the scope, so `fix: handle empty config` and `fix(my-package): handle empty config` behave the same way. A scope is still useful for human readers.

### The release PR

When commits that touch a package land on `main`, release-please opens (or updates) a single standing pull request titled something like `chore: release main`. That PR contains, for each affected package:

- the version bump in `pyproject.toml`
- a new section in that package's `CHANGELOG.md`

The release PR keeps updating as more changes merge. Nothing is released until someone merges it. Merging the release PR creates the `<package>-vX.Y.Z` tag and GitHub Release, and the same workflow run then publishes the package to Nexus.

### Publish guards

Even though release-please sets the tag and version together, the build workflow keeps two independent checks as a safety net:

1. **Tag/version match.** The version in the tag must equal the version in `pyproject.toml`.
2. **No duplicate versions.** The workflow queries Nexus for the package and version and fails if it already exists. A failure here always indicates a mistake, so the workflow fails rather than silently skipping.

### Reusable workflows (non-package changes)

Changes to reusable workflows follow the existing process: the PR title check still applies, no package release is triggered, and a maintainer cuts a repo-wide `vX.Y.Z` release and moves the rolling `vX` pointer.

Repo-wide releases must pass an explicit starting tag when generating notes (for example `gh release create v1.8.1 --generate-notes --notes-start-tag v1.8.0`). Without it, GitHub picks the most recent tag of any kind as the starting point, which may be a package tag, and the notes will be wrong.

## Developer walkthroughs

### Changing a Python package

A developer needs to add a retry option to a package in `python/<package>/`.

1. They branch from `main`, make the change, and add tests. They do not touch the version or the changelog.
2. They open a PR titled `feat: add configurable retry`. The PR title check passes and the package's PR workflow runs its tests.
3. After review, they squash-merge. The squash commit message is the PR title.
4. release-please updates the standing release PR: the package's version goes from `1.2.0` to `1.3.0` and its `CHANGELOG.md` gains a `1.3.0` entry with a link to the PR.
5. When the team is ready to ship, a maintainer reviews and merges the release PR. The changelog text can be edited in the release PR before merging if needed.
6. The workflow creates tag `<package>-v1.3.0` and a GitHub Release, verifies the tag matches `pyproject.toml` and that `1.3.0` is not on Nexus, then builds and uploads.

If the developer had titled the PR `update retry stuff`, the title check would fail with a message explaining the format. They fix it by editing the PR title. No rebasing is needed.

### Changing a reusable workflow

A developer fixes a bug in a shared container release workflow.

1. They open a PR titled `fix: correct image tag on container release`. The title check passes. No package paths changed, so no package checks run.
2. They squash-merge. release-please ignores the commit because it does not touch any configured package path.
3. A maintainer cuts the next repo-wide release (for example `v1.8.1`) with `--notes-start-tag` set to the previous repo-wide tag, and moves the `v1` pointer.

### A PR that touches both

If one PR changes a package and a reusable workflow, release-please still includes it in that package's next release, and the workflow change ships with the next repo-wide release. Keeping package and workflow changes in separate PRs produces cleaner changelogs and is preferred.

## Implementation

### 1. PR title check

`.github/workflows/pr-title.yml`

This check uses no third-party actions. The title is passed through an environment variable rather than inlined into the script, which prevents a malicious title from injecting shell commands.

The repository variable `PR_TITLE_ENFORCE` controls the mode. When it is unset or `false`, invalid titles produce a warning and the check passes. When it is `true`, invalid titles fail the check. Make the check required in branch protection once enforcement is on.

```yaml
name: PR title check

on:
  pull_request:
    types: [opened, edited, synchronize, reopened]

permissions:
  pull-requests: read

jobs:
  conventional-title:
    runs-on: ubuntu-latest
    steps:
      - name: Validate Conventional Commit title
        shell: bash
        env:
          TITLE: ${{ github.event.pull_request.title }}
          ENFORCE: ${{ vars.PR_TITLE_ENFORCE }}
        run: |
          pattern='^(feat|fix|perf|refactor|docs|test|build|ci|chore|revert)(\([a-z0-9._/-]+\))?(!)?: [^ ].+'

          if [[ "$TITLE" =~ $pattern ]]; then
            echo "PR title is valid: $TITLE"
            exit 0
          fi

          msg="PR title must follow Conventional Commits, for example 'feat: add retry option' or 'fix(my-package): handle empty config'. Allowed types: feat, fix, perf, refactor, docs, test, build, ci, chore, revert. Add ! before the colon for breaking changes."

          if [[ "$ENFORCE" == "true" ]]; then
            echo "::error title=Invalid PR title::$msg"
            exit 1
          else
            echo "::warning title=Invalid PR title::$msg"
            exit 0
          fi
```

Behavior of the pattern:

| Title | Result |
|---|---|
| `feat: add retry` | Pass |
| `fix(my-package): handle expiry` | Pass |
| `feat!: drop Python 3.9` | Pass |
| `refactor(core)!: rename API` | Pass |
| `chore(ci): bump action` | Pass |
| `Feat: add` | Fail (type must be lowercase) |
| `feat:add` | Fail (space required after colon) |
| `update readme` | Fail (no type) |
| `fix: ` | Fail (empty description) |

The `edited` event re-runs the check when the title changes, and `synchronize` re-runs it on new pushes so the required status stays attached to the latest commit.

### 2. release-please configuration

`release-please-config.json` at the repository root. Add one entry per package.

```json
{
  "$schema": "https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json",
  "release-type": "python",
  "include-component-in-tag": true,
  "include-v-in-tag": true,
  "packages": {
    "python/<package>": {
      "package-name": "<package>",
      "component": "<package>",
      "changelog-path": "CHANGELOG.md"
    }
  }
}
```

`.release-please-manifest.json` at the repository root. Seed each entry with the package's current released version so release-please knows where to start.

```json
{
  "python/<package>": "1.2.0"
}
```

Notes:

- Only commits touching a configured package path are considered for that package. Workflow changes outside `python/` are ignored, which keeps repo-wide releases separate.
- For packages still below `1.0.0`, add `"bump-minor-pre-major": true` to that package's entry so breaking changes bump the minor version instead of jumping to `1.0.0`.
- The first run will want to write a changelog covering history since the seeded version. Seed the manifest with the latest version already on Nexus and, if needed, set `"bootstrap-sha"` to the commit of the last manual release so older history is excluded.

### 3. release-please workflow

`.github/workflows/release-please.yml`

The publish job is called from this workflow rather than triggered by the tag. Tags created with the default `GITHUB_TOKEN` do not trigger other workflows, so a separate `on: push: tags` workflow would never run.

```yaml
name: release-please

on:
  push:
    branches: [main]

permissions:
  contents: write
  pull-requests: write

jobs:
  release-please:
    runs-on: ubuntu-latest
    outputs:
      releases_created: ${{ steps.rp.outputs.releases_created }}
      paths_released: ${{ steps.rp.outputs.paths_released }}
    steps:
      - id: rp
        uses: googleapis/release-please-action@v4
        with:
          config-file: release-please-config.json
          manifest-file: .release-please-manifest.json

  publish:
    needs: release-please
    if: needs.release-please.outputs.releases_created == 'true'
    strategy:
      fail-fast: false
      matrix:
        package-path: ${{ fromJSON(needs.release-please.outputs.paths_released) }}
    uses: ./.github/workflows/python-build-package-nexus.yml
    with:
      package-path: ${{ matrix.package-path }}
    secrets: inherit
```

Pin `googleapis/release-please-action` to a full commit SHA rather than `@v4` if the organization requires pinned actions.

### 4. Changes to the shared build workflow

`.github/workflows/python-build-package-nexus.yml` becomes package-agnostic by taking the package path as an input. It checks out `github.sha`, which is the release commit that release-please tagged.

Add these inputs and guard steps before the build step. Adjust secret and variable names to match what the workflow uses today.

```yaml
on:
  workflow_call:
    inputs:
      package-path:
        description: Path to the package directory, for example python/my-package
        required: true
        type: string
```

```yaml
      - name: Read package name and version
        id: meta
        shell: bash
        env:
          PKG_PATH: ${{ inputs.package-path }}
        run: |
          python - <<'PY' >> "$GITHUB_OUTPUT"
          import os, tomllib
          with open(os.path.join(os.environ["PKG_PATH"], "pyproject.toml"), "rb") as f:
              project = tomllib.load(f)["project"]
          print(f"name={project['name']}")
          print(f"version={project['version']}")
          PY

      - name: Verify release tag matches pyproject version
        shell: bash
        env:
          PKG_PATH: ${{ inputs.package-path }}
          VERSION: ${{ steps.meta.outputs.version }}
        run: |
          component="$(basename "$PKG_PATH")"
          expected="${component}-v${VERSION}"
          git fetch --tags --quiet
          if ! git tag --points-at HEAD | grep -qx "$expected"; then
            echo "::error::Expected tag $expected on $(git rev-parse --short HEAD), found: $(git tag --points-at HEAD | tr '\n' ' ')"
            exit 1
          fi

      - name: Fail if version already exists on Nexus
        shell: bash
        env:
          NEXUS_URL: ${{ vars.NEXUS_URL }}
          NEXUS_REPOSITORY: ${{ vars.NEXUS_REPOSITORY }}
          NEXUS_USER: ${{ secrets.NEXUS_USER }}
          NEXUS_PASSWORD: ${{ secrets.NEXUS_PASSWORD }}
          NAME: ${{ steps.meta.outputs.name }}
          VERSION: ${{ steps.meta.outputs.version }}
        run: |
          count=$(curl -fsS -u "$NEXUS_USER:$NEXUS_PASSWORD" -G \
            "$NEXUS_URL/service/rest/v1/search" \
            --data-urlencode "repository=$NEXUS_REPOSITORY" \
            --data-urlencode "name=$NAME" \
            --data-urlencode "version=$VERSION" \
            | python -c "import json,sys; print(len(json.load(sys.stdin)['items']))")
          if [[ "$count" != "0" ]]; then
            echo "::error::$NAME $VERSION already exists in $NEXUS_REPOSITORY. Versions are immutable; release a new version instead."
            exit 1
          fi
```

The tag check assumes the directory name matches the release-please `component`. If they differ, pass the component as a second input.

Nexus may normalize package names (for example `my_package` versus `my-package`). Confirm which form the search API matches against in your instance before relying on the duplicate check.

### 5. Repository settings

- **Pull requests:** allow squash merging only, and set the default squash commit message to "Pull request title".
- **Actions:** enable "Allow GitHub Actions to create and approve pull requests" so release-please can open the release PR.
- **Branch protection on `main`:** require the PR title check once enforcement is on.
- **Tag rulesets:** restrict creation of `*-v*` tags to the release workflow and maintainers so packages cannot be tagged by hand.
- **Repository variable:** `PR_TITLE_ENFORCE`, set to `false` during rollout and `true` afterward.

## Known gotchas

- **Release PR checks do not run automatically.** Pull requests opened by `GITHUB_TOKEN` do not trigger workflows. If branch protection requires status checks, the release PR cannot be merged without them. Either exempt the release PR's required checks, or have release-please use a GitHub App token (passed via the action's `token` input) so checks run normally.
- **Tag-triggered workflows will not fire** for tags created by `GITHUB_TOKEN`. This is why publishing is called from the release-please workflow.
- **Repo-wide release notes** need `--notes-start-tag` once package tags exist, or they will start from a package tag.
- **Merge commits and rebase merges** bypass the PR title. With anything other than squash merges, release-please reads individual branch commits, which will not follow the convention.
- **Forcing a version.** To release a specific version, merge a commit with a `Release-As: 2.0.0` footer in its body, or edit the release PR.

## Adding a new package

1. Create `python/<package>/` with `pyproject.toml`, `README.md` (including a "Releasing" section that links here), and an empty `CHANGELOG.md`.
2. Add the package to `release-please-config.json` and seed `.release-please-manifest.json` with its starting version (for example `0.1.0`).
3. Add or reuse a PR workflow scoped to `python/<package>/**` for tests.
4. No changes to the release or publish workflows are needed.

## Rollout plan

| Phase | Change | Impact |
|---|---|---|
| 1 | Squash-merge only, default squash message set to PR title, PR title check in warning mode | Small |
| 2 | Enable release-please for one package, with publishing called from the release-please workflow and both publish guards in place | Medium |
| 3 | Set `PR_TITLE_ENFORCE` to `true` and make the title check required | Small |
| 4 | Add the remaining Python packages to release-please | Small per package |
| 5 (optional) | Evaluate moving reusable workflow releases to release-please as well, which would replace manual `vX.Y.Z` releases and pointer moves | Medium |

Phase 1 is useful on its own even if later phases are deferred, since consistent PR titles also improve repo-wide auto-generated release notes.

## Verifying the setup

- **Title check:** open a draft PR with an invalid title and confirm the warning (phase 1) or failure (phase 3), then fix the title and confirm it passes without a new push.
- **Path scoping:** merge a `fix:` PR that only touches a reusable workflow and confirm no release PR changes appear.
- **Release flow:** merge a `fix:` PR touching one package and confirm the release PR bumps only that package's version and changelog.
- **Tag guard:** in a test branch, call the build workflow on a commit with no matching tag and confirm it fails.
- **Duplicate guard:** re-run the publish job for an already published release and confirm it fails at the Nexus check, not at upload.
- **Repo-wide notes:** cut a test repo-wide release with `--notes-start-tag` and confirm package PRs are not included unexpectedly.
